# Milestone: Tile Component Refactor

**Status:** Pending
**Affected Slices:** `src/components/tile/` (new), `src/components/pool/`, `src/components/history-area/`, `src/components/submission-area/`, `src/components/instructions-screen/`, `docs/roadmap/1.x.x/1.4.x/`, module `README.md` / `SPEC.md` files

## Context

The current pool tile was recently expanded to carry several unrelated concerns at once:

- visual tile identity: dimensions, border, face, shadow, typography, hover/drop states
- character rendering: `resolveCharacter(tile.character)`
- pool-specific interactivity: tap, drag, drop on submission slots, drop on other pool tiles
- GSAP Draggable setup and drag lifecycle callbacks
- GSAP feedback animations: rotate squeeze, compose pulse, particle burst, entrance scale
- rejected-compose CSS shake feedback

This makes `src/components/pool/Tile.tsx` hard to edit when working only on the visual identity. The same tile visual language is also needed in multiple places:

- pool tiles: fully interactive, tappable, draggable, compose/drop aware
- submission area filled slots: interactive, tappable, draggable between slots / back to pool
- history area: inert evaluated tiles with result variants
- instructions screen: inert visual examples

The refactor should separate visual primitives from context-specific behavior. The immediate goal is not to redesign the final art direction, but to create a structure where visual iteration happens in a small base tile component and CSS module without requiring an agent/designer to read pool drag mechanics.

## UX Direction Update

Earlier 1.4.x notes may mention an "infinite" or free-positioned pool canvas. After UX/UI testing, the intended direction is **fixed tile slots / fixed layout positions**, not a freeform draggable canvas where tiles remain wherever dropped.

Implications:

- Pool tiles should visually return to their fixed pool layout position when a drag does not produce a successful move.
- Valid drag operations still dispatch reducer actions and let React render the new state.
- Responsive behavior should make tiles smaller or adjust layout density for smaller screens rather than introducing a pannable/infinite canvas.
- Any stale documentation describing free-positioned/infinite pool behavior should be corrected during this milestone.

## Target Architecture

Prefer explicit context components over a generic inheritance-like stack such as `Tile -> AnimatedTile -> InteractiveTile`.

Recommended structure:

```txt
src/components/tile/
├── BaseTile.tsx              # visual primitive; no game state, no GSAP, no resolveCharacter
├── BaseTile.module.css       # shared visual identity and visual variants
├── CharacterTile.tsx         # resolves a game Character into BaseTile content
├── use-tile-feedback.ts      # optional hook for shared tile feedback animations
├── README.md
└── SPEC.md

src/components/pool/
├── PoolTile.tsx              # pool-specific tappable/draggable tile; replaces current Tile role
├── PoolTile.test.tsx
├── Pool.tsx
├── README.md
└── SPEC.md
```

Layer responsibilities:

1. **`BaseTile`** owns tile visuals only. It should accept display children/content, element kind where needed, and visual state/variant props. It must not import game context, character helpers, GSAP, or reducer types.
2. **`CharacterTile`** is a small wrapper that accepts a `Character`, calls `resolveCharacter`, and renders `BaseTile`.
3. **`PoolTile`** owns pool-specific behavior: tap, GSAP Draggable, hit testing with `data-tile-id` / `data-slot-index`, drop callbacks, and pool-only animation flags.
4. **History, instructions, and submission components** should migrate to `BaseTile` / `CharacterTile` incrementally so they share visual identity while keeping their own behavior.

## Success Criteria

1. `src/components/tile/` exists with `README.md` and `SPEC.md`.
2. The shared tile visual identity can be edited primarily in `BaseTile.module.css`.
3. `BaseTile` has no imports from GSAP, game context, pool, submission, history, or character resolution helpers.
4. `CharacterTile` is the only shared tile component responsible for `resolveCharacter`.
5. Pool behavior remains unchanged from the user's perspective.
6. History, instruction, pool, and filled submission tiles share the same base visual language where practical.
7. Pool documentation no longer describes raw Pointer Events drag or an infinite/free-positioned canvas as the target behavior.
8. Relevant tests pass after each completed ledger item.

## Agent Notes

- Before changing a module, read that module's `README.md` and `SPEC.md` completely.
- Keep exported symbols at the top of files and unexported helpers below, per repository conventions.
- Use Hangul Compatibility Jamo in application code when adding visible Korean jamo examples.
- Prefer small props with clear visual names over a large generic `state` object.
- Avoid using `as` casts unless unavoidable; add an inline explanation if one is needed.
- Do not introduce new animation libraries or styling systems. Keep React 19, TypeScript strict, CSS Modules, native CSS, Vite.
- GSAP belongs in behavior/animation hooks or context-specific components, never in `BaseTile`.
- If a migration step uncovers unclear visual decisions, preserve current appearance and document the open decision rather than inventing a new art direction.
